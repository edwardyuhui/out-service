**IndusOpt 平台、模型与答辩的整体修改方案**

审阅日期：2026-09-25。代码基线：`f832237`。本文是修改建议与设计规格，尚未实施这些变更。

建议把下一版定位成“面向工业建模工程师的建模数据准备与模型验收工作台”。产品主线是：工程师提交一项建模任务，系统帮助判断数据是否够用、筛选哪些片段、模型是否可信，并交付可以复核的数据与模型。现阶段能够成立的闭环是建模流程的反馈寻优。生产设定值优化、节能降耗与控制系统投运需要另外的模型、约束、试点和验收证据。

本次阅读了模型与优选实现、寻优与评价策略、Agent 编排和执行状态、清洗及版本服务、主要前端页面、历史实验报告；检查了 8/10/11/17 页等多个 PPT 版本的文本与结构，并查看了已有 PPT 总览和平台截图。资料包里的 11 页 PPT 为主要修改对象，8 页版用于了解目前的口头讲述。浏览器访问本地前端时返回 `ERR_BLOCKED_BY_CLIENT`，因此本次界面意见基于源码及已有截图，没有把它当成一次最新版本的运行验收，也没有重新跑模型实验。

**先保留已经做好的部分，再集中修正影响可信度的问题。**

平台已经有实际算法、数据版本血缘、时滞与变量处理的人工确认、Agent 执行状态持久化、独立 Test 评价、残差及泛化诊断、任务与报告产物。这些构成了可继续开发的基础。下一阶段不宜同时重写前后端、替换整套算法并加入大量新模型；应让现有链路产生一组能解释、能重算的真实过程数据结果。

最需要补足的是：评价与优选口径、真实数据外部验证、以工程任务为中心的产品操作、统一事实来源、面向评委的案例叙述。

**模型修改的第一步是让现有计算与评价准确。**

1. **修正寻优误差的归一化。** [optimization_service.py](</Users/maguayuhui/Documents/竞赛/服外 9.22/service-outsource/backend/app/services/optimization_service.py:283>) 当前把验证集 RMSE 除以 `abs(val_fit)`。FIT 是百分比形式的拟合指标，不能充当输出量纲的尺度。同一输出换单位后，这个惩罚项会发生不应有的改变。建议用训练集确定的输出标准差或稳健尺度归一化自由仿真 RMSE，并明确零方差处理。更易解释的初版是：先检查模型适用性和必需约束，再按验证集自由仿真误差排名，近似持平时选更简单、数据更少的方案。若继续使用复合权重，必须给出权重版本及敏感性分析。当前缺失残差白度时直接替换成 1.0，也应改成“诊断不可用”，避免获得最好评价。

2. **修正重叠窗口的信息量重复计算。** [selection.py](</Users/maguayuhui/Documents/竞赛/服外 9.22/service-outsource/backend/algorithms/identifiability/selection.py:333>) 用去重后的行数计算预算，但仍把整块窗口的 Gram 矩阵加入信息矩阵，最终训练又通过 `np.unique` 去重。因此重复行在选择目标里被累计，在最终训练里只出现一次。默认步长为半个窗口，确实允许重叠。可先用不重叠候选窗口建立清晰基线；保留重叠时，应按尚未选入的行重新计算边际贡献，让最终唯一行集合与信息矩阵完全一致。超过行预算的候选应判断是否还有其他可行候选。修改后重新检查 lazy greedy 与朴素实现的一致性，也重新审查 PPT 中 `1−1/e` 保证的约束前提，不能直接把基数约束结论套到去重行预算。

3. **统一整条链路的时间分区。** [segment_service.py](</Users/maguayuhui/Documents/竞赛/服外 9.22/service-outsource/backend/app/services/segment_service.py:114>) 按回归矩阵行数比例划训练区；[modeling_service.py](</Users/maguayuhui/Documents/竞赛/服外 9.22/service-outsource/backend/app/services/modeling_service.py:140>) 按原始样本长度并减保护区。二者不是同一种边界定义。缺失行及不同滞后会进一步影响边界。应先冻结原始时间轴上的 train/validation/test 范围和保护区，让清洗、选段、时滞、变量筛选、模型拟合共用。

4. **把清洗策略纳入分区约束。** [cleaning_service.py](</Users/maguayuhui/Documents/竞赛/服外 9.22/service-outsource/backend/app/services/cleaning_service.py:100>) 目前把整份版本交给清洗流水线。若先在全量上估计 IQR、均值或其他统计量，再切训练与测试，会污染评测；跨边界插值和平滑也需要防护。正式评测应只在训练区估计统计参数，固定参数处理后续区间，保留原始值、修改掩码和来源。测试目标中被插补、平滑的点不能悄悄作为真实观测计入成绩。scikit-learn 的[数据泄漏指南](https://scikit-learn.org/stable/common_pitfalls.html)明确要求训练数据独立学习预处理参数。

5. **统一指标、曲线与诊断使用的样本范围。** 当前 `_metrics` 对 validation 使用保护区，而 `validate_model` 接收完整的 train_end 到 val_end；两处 FIT 计算的下限处理也不完全一致。应建立一个评价对象，保存预测模式、初始状态策略、样本索引、指标定义和分区版本，界面、寻优与报告读取同一结果。不能一张页面同时出现两种范围计算出来的“验证 FIT”。

6. **补齐工作点偏置与单位处理。** 当前 ARX 回归结构没有常数项，拟合入口也未见统一的训练工作点中心化及尺度变换。真实温度、流量和压力通常有非零基值，不同变量的单位也影响 Ridge 与带固定正则项的信息量计算。保存训练区工作点、均值或稳健中心、尺度、单位及反变换，让报告输出回到工程单位；优选与建模使用同一变换。是否去趋势应根据过程特征决定。MathWorks 的[系统辨识预处理说明](https://www.mathworks.com/help/ident/preprocess-data.html)将偏置、漂移及采样问题列为模型估计前的检查项。

7. **让搜索空间与实际执行一致。** 当前 `_structure_grid` 固定扫描 na=1–4、nb=1–3、OLS 与 alpha=0.1 的 Ridge；外部声明的某些搜索范围没有进入该网格。寻优又将一个 nk 用于全部输入通道。建议界面明确实际网格；按已确认的每通道时滞搜索小范围修正，并记录原始物理时滞和补偿后剩余时滞，避免重复补偿。补偿版本的 nk=0 必须有血缘依据。

这些是静态阅读发现的实现问题与风险点。需要在修正后用针对性检查和重新评测判断影响范围，不宜直接继续引用旧的最佳结果。

**模型能力的扩展建议按实际数据暴露的问题推进。**

| 能力层 | 建议 | 用途与限制 |
|---|---|---|
| 基础对照 | 保留持久性预测、全量 ARX、Ridge ARX | 判断模型是否超过简单预测，以及优选是否真的有效 |
| 第一阶段升级 | 完善 ARX 的偏置、尺度、时滞、约束与诊断 | 先让现有模型可靠处理真实记录 |
| 下一种模型 | 增加一种线性状态空间辨识方案 | 检查更丰富的动态及多输出需求；实现成本高于再加一种回归器 |
| 非线性候选 | 在残差和跨工况结果显示需要时加入 NARX，或按工况建立局部模型 | 先与线性基线比较滚动验证表现，递推稳定性需单独检查 |
| 深度时序模型 | 数据量和独立验证充分后再评估 TCN/LSTM 等 | 867 点短记录不足以支撑“模型越大越高级”的判断 |
| 过程控制与经济优化 | 后续独立模块 | 需要操作变量、扰动、约束、经济目标与闭环验证；当前不应作为已实现能力 |

模型选择应考虑数据量、非线性、噪声、开环/闭环采集方式及用途。高相关和低 VIF 不等于因果关系。对在反馈控制下采集的数据，要识别反馈与噪声相关问题，再考虑合适的噪声模型、工具变量或闭环辨识方法。针对积分型过程，稳定性验收也应按模型类别设计，不能对所有对象使用同一个简单阈值。MathWorks 的[模型估计排障说明](https://www.mathworks.com/help/ident/ug/troubleshooting-models.html)同样建议根据验证与残差诊断调整模型结构。

最终模型卡至少应显示：用途、输出与单位、训练与评价时间范围、有效数据比例、独立 Test 误差、自由仿真及指定预测时域结果、稳定性/过程先验检查、残差与输入的相关性、适用工况、明确的失败原因、版本和复现入口。自由仿真 FIT 不能改名为“准确率”；存在近常量输出时，FIT 可能不适合比较，应同时给工程单位的 MAE/RMSE。真实数据没有参数真值时，不报告参数相对误差。

**大模型与 Agent 的升级，应让它作出有依据的下一步建议。**

现有 LLM 规划、工具白名单、规则回退和确认节点值得保留。产品可进一步把任务目标、变量角色、采样间隔、质量诊断、工程约束和允许的搜索预算变成结构化上下文。输出计划要说明“为什么做这一步”和“通过什么条件才能继续”。当前执行状态机能标记失败，下一步可增加少量确定性的恢复分支：样本不足时调整窗长或申请更多数据、秩不足时提出扩大覆盖或正则化、泛化下降时结束交付并提供诊断。每个分支限制重试次数和耗时。

确认页不要只给“确认/取消”，应显示调整的对象、当前与建议值、证据图、受影响的数据版本和撤回方式。LLM 负责把结构化结果解释给工程师，指标依然由算法与数据库提供。测试集的评价结果不进入同一次寻优的反馈回路。

目前不建议优先微调或只换一个更大的语言模型。先准备约 30–50 条任务作为内部工程评测集，覆盖中文变量别名、缺单位、多个输出、低置信时滞、无有效数据、失败恢复、网络中断及不支持的请求，统计任务完成率、参数正确率、错误动作拦截与解释、延迟和成本。数量是建议的起步工作量，不是已经完成的实验。

[DaISy 本地说明](</Users/maguayuhui/Documents/竞赛/服外 9.22/公开工业数据集/DaISy/README.md>)已经列出 dryer2、evaporator 和 glassfurnace。本次查看的实验目录及这份本地 SQLite 未找到它们的完整评测，SQLite 中可见的两个数据集均为 simulation；这不能排除其他数据库存在另外的结果。应先把已经完成的真实数据运行记录统一收集，再决定缺什么。

| 数据 | 建议验证任务 | 必须保留的信息 |
|---|---|---|
| 工业干燥机 dryer2，867 点 | 作为主讲案例；选择一个输出，分析燃料、风机、进料对它的动态关系 | 官方采样间隔 10 秒；短记录，搜索预算需小 |

| 玻璃炉 glassfurnace，1247 点 | 分别评估多个温度输出，发现不同测点的模型差异 | 当前 MISO 每次只拟合一个输出；1 秒也是占位间隔 |

评测同时回答两个问题：同一模型下哪种选段更好，以及同一数据下哪种模型更合适。将这两条比较混在一个排名里，会无法解释提升来自哪里。

选段对照至少包括全量训练数据、随机连续片段、能量法、质量评分法、D-最优。除全量参考外，各方法使用相同的唯一训练行预算和相同的保护区。使用连续片段，保留原始时间索引，禁止把不相邻片段硬拼成一条连续时序后构造滞后。每个方法都可以获得相等的模型搜索机会，并同时报告总耗时。

评测流程为：冻结尾部 Test；在此前数据上做按时间滚动的训练/验证；只根据验证结果决定预处理、超参数及模型；选定后评价冻结 Test。小数据可先用两到三个合理的时间切分，保证每段足够长，避免为了增加折数把动态片段切碎。修改方案若利用了 Test 的失败结论，需要另留新的最终评价数据，不能反复用同一 Test 挑最优。实现可参考[按时间划分并设置 gap](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)的做法。

交付一张真实结果表，至少含：数据集/输出、模型、策略、原始训练行数、唯一选中行数、验证与 Test 的自由仿真 FIT、工程单位误差、运行耗时、失败数和原因。记录每次原始结果；随机重复只衡量随机策略波动，不把同一工业序列的重复运行说成多家工厂验证。时间序列的区间估计需要考虑相关性，不用逐点独立重采样包装高置信。

干燥机案例可以讲“使用公开工业过程数据开展离线验证”。只有拿到企业真实合作和部署记录后，才改成企业试点案例。若暂时还没有性能提升，应展示诊断与失败边界，不能填入预期数字。

| 新建任务 | 数据是什么，准备做什么 | 装置/记录名称、目标输出、单位、采样周期、输入角色、时间范围、用途；有单位字段则完善来源和校验，不重复造字段 |
| 数据概览 | 哪些问题会影响建模 | 一张大时间序列图和关联的问题列表；点缺失或冻结项定位到图；原值与处理值可切换 |

| 工作台 | 当前结论、证据和下一步 | 顶部任务上下文，左侧步骤，中部主要证据，右侧建议/人工确认；常用图形区域宽度优先 |

| 寻优 | 相比基线实际改进了什么 | 第一屏给模型表现、数据量、总耗时及失败次数；Trial 编号、目标函数组成和参数表放详情；替换手填 UUID 为版本选择器 |
| 报告与交付 | 工程师拿走什么 | 概要、适用范围、曲线、指标来源、配置、数据和模型文件；增加易阅读的 PDF 工程摘要，保留机器可读产物 |
| 历史任务 | 两次尝试为什么不一样 | 支持同项目比较版本、数据区间、预处理、模型和结果；优先比较变动项 |

结果区的默认信息顺序为：结论、关键证据、下一步动作、技术详情。可采用这样的表达：“本次模型未通过约定的离线验收；验证区间较好，尾部 Test 明显下降；建议检查工况变化。”这里的判断必须由实际阈值和结果生成，不能写死成“推荐”。

现有中英文混排也应统一：面向工程师的默认界面写“独立测试集”“自由仿真”“一步预测”，技术缩写放括号或说明中。保留专业用户的原始 JSON 与 UUID 查看入口。功能菜单可逐步由算法名称改为任务名称，例如把“Optuna 闭环寻优”改为“改进建模方案”。

平台视觉建议沿用现有的浅灰、白色与深草绿色，提升字号、对比度和主图比例。不要把所有页面都换成深色工业大屏。常用正文建议 14–16 px，重要结果和图表标记明显更大；减少卡片套卡片，让同一页只有一个主要操作。错误、待确认、完成状态必须同时有文字和形状区别。

平台动效服务于操作反馈：侧面板开合约 180–240 ms，选段高亮约 150–250 ms，任务进入新阶段只轻量更新一次。长任务的进度依据真实阶段或已完成 Trial 数，不能用计时器把未知进度伪装成精确百分比。保留减少动效设置，图表持续跳动和首页循环动画不应干扰工作。

工程部署方面，README 明确尚无管理员登录权限系统，当前适合受信任的本地环境。进入多人企业试点时，补项目权限、设置页权限、备份恢复、部署自检、任务超时与重启恢复验收。已有 RQ 和失败状态处理应继续完善，不能只因有代码就称部署通过。第一阶段接入可用只读 CSV/历史库导出，后续再按实际接口需求建设连接器。

**让案例真正具备落地说服力，需要补工程证据。**

可按三层表达：已经实现的本地可运行功能；已经完成且有报告的离线验证；拟开展的企业试点。三层分别标清状态。现阶段主要价值可以量化为准备数据的时间、人工确认次数、完成一个合格模型所需迭代数、可用数据比例及失败识别能力。计时从相同起点开始，记录人工操作和机器运行时间。没有人工对照时，不写“效率提升多少倍”。没有生产验收时，不写节能百分比或客户收益。

建议用一个具名的案例目录保存原始文件来源、数据许可/使用说明、原始数据哈希、变量映射、分区、预处理参数、模型、指标、报告、截图与演示视频。实际 PPT 截图、曲线、数字从这个案例目录导出。每次算法变更生成新版本，保留旧版本用于解释历史结果。
