# IndusOpt 项目简介 PPT · 设计稿

**用途**：2026「数字马力杯」第十三届浙江省大学生服务外包创新应用大赛 A14 初赛提交材料。
根据官方《参赛指南》（`附件2`），这份 PPT 对应提交材料里的 **S3：核心内容展示（Presentation）**——"以 PPT 等形式介绍和展示方案的思路和核心内容，10 分钟以内为宜"。
区别于已有的 [`IndusOpt-A14-答辩.pptx`](../IndusOpt-A14-答辩.pptx)（决赛答辩阶段用，靠人讲）——S3 是网评复赛阶段用，**必须自己把话说完**，评委不会听你解释。

**页数**：17 页（官方赛题手册给的格式上限是 20 页 / 20M；"10 分钟以内为宜"是指南对讲解节奏的建议，如果你们打算给 PPT 配语音/短视频解说，控制在 10 分钟内）。
**画布**：16:9，13.333in × 7.5in（沿用 `build.js` 的 `LAYOUT_WIDE`）。

### ⚠️ 合规红线（违反直接取消资格，比设计好看更优先）

《参赛指南》"原创承诺要求"明确写了：**提交材料中不得出现参赛学校名称、指导教师姓名，及任何暗示性的图片/照片/图像/链接，打包文件的文件名或目录名也不能出现**；可以给团队取一个昵称，队员姓名尽量用角色或昵称代替。

《参赛指南》里还有两份和这份 PPT 平级、但不属于这份 PPT 范围的材料，提醒一下别漏交：

### 字体（三级体系，不是从头到尾一种字体）

只用三种字体，全部是 Windows / Office 原生自带、不需要额外安装的字体——这一点是硬约束，不是审美偷懒：现有答辩 PPT 的 README 里已经写过真实教训（"若在其他环境打开出现字体回退，行宽会变化，需重新检查是否有文字换行超框"），评委电脑大概率是标准 Windows + PowerPoint，引入一个对方机器上没装的"好看字体"，换来的是不可控的文字溢出风险，不值得。三级字体本身就足够制造层次差：

| 层级 | 字体 | 用在哪里 | 字重/字号 |
|---|---|---|---|
| **标题** | 微软雅黑 Bold | 封面主标题、每页页眉标题、章节名、大字结论句（如 P5 的归因句、P9 结尾的总结语） | 20–44pt，加粗 |
| **正文** | 微软雅黑 Regular | 段落陈述、表格文字、卡片说明、图例、页脚、eyebrow 小字 | 11–16pt，常规字重 |
| **数据/代码** | **Consolas** | 所有独立展示的数字（14.3%、200、237、96.5、28.5倍……）、实验编号（`EXP-2.1`）、代码/字段标识符（`requires_confirmation`）、公式与希腊字母变量（`log det(λI + Σ ΦᵀΦ)`）、纯英文技术名词（`FastAPI`、`Docker Compose`、`vue-tsc --noEmit`） | 与所在文字同级字号，通常加粗；颜色用 `AMBER` 或 `RUST` 上色制造视觉锚点 |

**为什么第三级单独拎出来**：这份 PPT 里最有说服力的内容大多是具体数字和真实的代码/实验标识符（`14.81% 对 14.82%`、`requires_confirmation`、`EXP-2.1`），中文字体渲染西文数字和符号时字宽不均匀、观感发虚；换成等宽字体后这些数字/代码会像"仪表盘读数"一样干净利落，跟整份 PPT 深蓝控制室的视觉气质也是呼应的——这不只是为了不单调，是让证据类内容在视觉上就比陈述性文字更"硬"。

**默认规则**：下面每页的详细设计里，凡是没有单独标注"字体"的地方，一律按标题=雅黑 Bold / 正文=雅黑 Regular 的默认两级处理；只在某页出现值得用 Consolas 的数字或代码标识符时，才会在该页单独注明具体用在哪几处。

### 版式母版（每张内容页统一遵守，评委翻页时会本能地按这个节奏找信息）
- **页眉**：左上角 `M(0.7in, 0.52in)` 处一个直径 0.52in 的实心圆"徽标"，内填白色加粗页码数字，圆的颜色 = 该页所属章节色；徽标右侧同一基线放页面标题（22-24pt 加粗）。
- **页脚**：细分隔线 + 左侧 "IndusOpt · A14 项目简介"，右侧页码，`MUTE` 色 10pt。
- **正文区域**：页眉下方到页脚上方，左右各留 `M=0.7in` 安全边距。
- **章节色条**：四个章节各用一种强调色贯穿该章节所有页面的徽标颜色，让评委即使跳页看也能靠颜色判断"现在在哪一段"。

## ⚠️ 关于"页面切换动画"的实现须知（先读这段，避免返工）

`pptxgenjs`（现有 `build.js` 用的库）**不提供稳定的幻灯片切换动画 / 元素进入动画 API**——它只负责把静态内容（文字、形状、图表、图片）写进 OOXML，动画和切换属于 PowerPoint 的 `<p:transition>` / `<p:timing>` 节点，脚本生成不了。

所以下面每一页写的"切入动画"，实际落地路径是：

1. **脚本仍按现有方式生成静态内容**（`node build.js` 同款做法，出一个新的 `IndusOpt-A14-项目简介.pptx`）；
2. **在 PowerPoint 里手动应用一遍下表的切换效果**——"切换"选项卡逐页点选即可，17 页大概 10–15 分钟，比看起来快，因为大部分页面用的是同一个"淡出"；
3. 章节边界（P2→P3、P4→P5、P9→P10、P13→P14）用的是"华丽型"效果，PowerPoint 里名字和下表一致，直接找。

不建议尝试用脚本硬注入切换 XML——answer PPT 的 README 里已经写了"本环境 LibreOffice 不可用、无法渲染复核"，手工注入的 XML 一旦格式有误会在你们自己都看不到问题的情况下坏掉整个文件，风险大于省下的 15 分钟。

### P1 · 封面

**背景**：`INK` 深色。

**内容**：
- Eyebrow（小字，`INV_MUTE`，14pt，字间距放宽）：`2026「数字马力杯」第十三届浙江省大学生服务外包创新应用大赛 · A14（和利时）`
- 主标题（44pt 加粗，白色）：`IndusOpt 工模智优`
- 副标题（20pt，`INV_MUTE`）：`基于 Agent 的流程工业建模数据智能优选与闭环寻优系统`
- 三张关键数字卡片（横排，`NAVY` 底 + `TEAL` 细边框）：
  1. `14.3%` 数据量 → 达到全量数据辨识精度
  2. `200` 个工作点 → 结论稳健性验证
  3. `237` 项 → 后端自动化测试通过
- 底部一行（`MUTE` 转 `INV_MUTE`，12pt）：团队昵称 **【待填，不可含校名/学院名】** · 日期 —— **不放指导教师信息，官方原创承诺要求禁止出现**

**布局**：文字块左对齐占左侧 56% 宽度，纵向居中堆叠（eyebrow → 主标题 → 副标题 → 数字卡片行，间距依次 0.3in / 0.25in / 0.5in）。右侧 44% 放项目图标 [`assets/icon.svg`](assets/icon.svg)（闭环信号标：`TEAL` 闭环箭头 + 中央 `AMBER` 高亮波形，视觉隐喻"从平稳信号里挑出高信息片段"，呼应整份 PPT 的核心叙事），放大到页面右侧居中，直径约 3.5in。这个图标同时也是全片唯一的品牌标记，不需要在其他页重复出现。

**字体**：主标题、副标题用雅黑 Bold；eyebrow、底部团队信息用雅黑 Regular；三张卡片里的 `14.3%`/`200`/`237` 三个数字单独用 **Consolas** 加粗、`AMBER` 上色——封面第一眼就要让评委看出"这是有硬数字支撑的项目"，不是纯文字堆砌。

**进入动画（页内元素，非页面切换）**：eyebrow 淡入 → 主标题从下方 0.3in 处推入+淡入 → 副标题淡入 → 三张卡片从左到右依次淡入，间隔 0.15s。这组是全片唯一值得手动加元素动画的地方，开场定调即可，后面页面不必再逐条加，避免评委看疲。

### P5 · 我们把"标准答案"实现了一遍（全片最强钩子）

**背景**：`PAPER`。徽标 `01`（章节 02 从这页开始），`AMBER`。

**标题**：`我们把"标准答案"实现了一遍——然后发现它不成立`

**内容**：
- 简述现有两条路线：
  - **人工圈选**：慢、不可复现、因人而异
  - **加权质量评分**：滑动窗口算能量/信噪比/响应关联度等特征，加权求和取前 K 段——**赛题任务清单本身写的就是这套特征**
- 核心陈述（大字，居中或偏左，全片视觉重心）：
  - `14.81%` （`RUST` 色，36pt 加粗）　对比　`14.82%`（`MUTE` 色，36pt）
  - 下方小字：`按规范原样实现加权评分，10 组种子对照实验：在激励不均匀的数据上，加权评分与"只看输入变化能量"没有区别，两者都秩亏`

**内容**：《参赛指南》"大赛原则"明确要求团队必须包含**项目负责人、技术负责人、客户关系经理**三个角色，且要在方案里体现各自职责——这不是可选项，是团队组织环节的评审依据之一，也对应网评评分表里"项目展示**与团队协作**"这一项（20%）。三张等宽角色卡片，横排：

| 角色 | 官方职责定位 | 在本项目里对应的实际工作 |
|---|---|---|
| **项目负责人**（PM） | 团队合作中的领导力、组织力、管理能力；对应 S2B 组织管理与业务分析 | 【待填，如：整体进度把控、阶段验收、赛事材料统筹】 |
| **技术负责人**（技术经理） | 团队合作中的技术水平和主导力；对应 S2C 技术路线及实现方案 | 【待填，如：算法设计（D-最优优选、闭环寻优）、后端架构】 |
| **客户关系经理** | 团队合作中的沟通、协调、交际能力；对应 S2D 成本模型及可行性分析 | 【待填，如：需求对接、产品交互设计、可行性与成本分析】 |

**成员姓名**：《参赛指南》"原创承诺要求"写的是"参赛队员姓名尽可能用角色或昵称代替"——卡片上建议直接写角色名（"项目负责人""技术负责人""客户关系经理"）或昵称，不写真实姓名+学号也完全合规，更省心。**指导教师姓名一律不能出现在这页或任何一页。**

> 三个角色的具体人选和职责描述，在 [`分工与过程文档.md`](分工与过程文档.md) 里目前还是【待填】占位——这页开工前请先把那份文档的表格填完并对齐这三个官方角色（不是自由命名的"前端/后端/算法"），这页直接照抄即可。
